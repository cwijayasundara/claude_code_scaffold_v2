# Spec System

> Specs are the source of truth. All code traces back to a spec.

## Dual-Track Architecture

### Track A: XML App Spec

```
specs/app_spec.xml
    ↓  /init-from-spec (or bash scripts/init-from-app-spec.sh)
specs/feature_list.json    ← master registry of all features
specs/features/*.md        ← one spec per feature (stubs, then fleshed out)
```

**Best for**: Greenfield projects where you can define the full app upfront.

**Template**: `specs/templates/app_spec_template.xml`

### Track B: Interview-Driven

```
/interview
    ↓
docs/requirements.md       ← gathered requirements
    ↓  /decompose
docs/backlog/*.md          ← user stories
specs/features/*.md        ← one spec per feature
```

**Best for**: Iterative projects or when requirements emerge through discovery.

### Convergence

Both tracks produce the same artifact: `specs/features/<name>.md`. From there, the workflow is identical:

```
specs/features/<name>.md → implementer agent → src/ + tests/
```

## Feature Spec Anatomy

Every spec in `specs/features/` follows the template at `specs/templates/feature_spec.md`:

| Section | Purpose |
|---------|---------|
| Title & ID | Unique identification |
| Description | What the feature does |
| Motivation | Why it's needed |
| Acceptance Criteria | Testable Given/When/Then statements |
| Affected Layers | Which layers need changes |
| Data Model Changes | New types, schemas |
| API Changes | New/modified endpoints |
| Dependencies | Other features, external services |
| Test Strategy | What to test and how |
| Estimated Complexity | Small/Medium/Large |

## Spec-to-Code Traceability

```
specs/features/auth.md         → src/service/auth.py
                               → tests/unit/test_auth.py (# Spec: auth)
specs/features/user-profile.md → src/service/user_profile.py
                               → tests/unit/test_user_profile.py (# Spec: user-profile)
```

Enforced by:
- `spec_coverage.sh` — service modules must have a spec
- `spec_acceptance_traceability.sh` — tests must reference spec criteria

## Spec Lifecycle

```
draft → review → approved → implemented → verified
```

| Status | Meaning |
|--------|---------|
| draft | Initial creation, may have gaps |
| review | Ready for human review |
| approved | Accepted, ready for implementation |
| implemented | Code written and tests passing |
| verified | Acceptance criteria validated end-to-end |

## Feature List Registry

`specs/feature_list.json` tracks all features:

```json
{
  "app_name": "my-app",
  "features": [
    {
      "id": "auth",
      "name": "Authentication",
      "priority": "high",
      "status": "pending",
      "spec_file": "specs/features/auth.md"
    }
  ]
}
```

This file is auto-generated by `scripts/init-from-app-spec.sh` and should be updated as features progress through the lifecycle.
